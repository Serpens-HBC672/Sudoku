# 2048 TD 搜索深度历史实验与文献分析报告

日期：2026-10-06  
分析对象：`Serpens-HBC672/Sudoku` 的 `codex/2048-expectimax-32768` 分支  
核查版本：`d368eb7870cdd7e8ae400ee67d628ef033c3bbdf`

## 一 结论

**增加搜索深度值得验证，但现有证据不能证明把当前程序改成固定 3-ply 或 4-ply，就能稳定获得第二个 32768 或合成 65536。** 本项目已经验证的是“8×6 TD 权重、常规两层、困难局面三层”到达第一个 32768 的能力。固定三层、固定四层，以及继续冲击 65536，均没有本项目的受控对照成绩。

还应先解决目标边界：当前 TD 求解器主动在 32768 停止，其目标参数、棋盘编码和移动路径也限制了继续搜索。取消页面上的停止提示，并不等于 TD 搜索已经支持 65536。至于达到首个 65536 后立即结束，和继续评价包含 65536 的棋盘，是两个工程范围不同的问题。

本报告整理历史记录、当前实现与外部研究，并提出待执行的实验方案；本次没有修改仓库代码、训练权重或运行新一轮游戏基准。

## 二 历史实验实际说明了什么

### 项目内可以追溯的结果

以下三个开发配置使用相同的十个种子 `60002–60011`，目标都是首次达到 32768。

| 配置 | 达到 32768 | 平均单局时间 |
|---|---:|---:|
| 4×6 权重，固定 2-ply | 2/10 | 1.53 秒 |
| 8×6 权重，固定 2-ply | 3/10 | 3.20 秒 |
| 8×6 权重，选择性 3-ply | 8/10 | 6.74 秒 |

选择性三层仅在当前棋盘“空格数不超过 1，且最大块至少为 8192”时触发，其余动作仍用两层。开发结果显示了值得进一步验证的收益，同时计算时间增加；但十局样本很小，而且参与了策略选择，不能把 8/10 当作该策略真实胜率为 80% 的证明。[项目实验记录](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/EXPERIMENTS.md)

随后冻结配置，在全新的种子 `61001–61100` 上完成独立评估：**49/100 达到 32768，95% Wilson 区间为 39.4%–58.7%**；没有中止、超时或缺失。由于首次 32768 即停止，这一实验没有测量第二个 32768，也没有测量 65536。

版本归属需要保留：上述成绩属于当时冻结求解器 SHA-256 `ab2e0c4eca2e84061602f9d4b80a45debd9986a35a618f32478cb0ae097261ed`。当前版本后来加了 packed 输入边界校验，仓库记录了行为一致性回归，但没有重跑独立一百局，旧成绩不能重新标成当前源码的新实测。[冻结配置与后续变更说明](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/EXPERIMENTS.md#冻结配置与独立性)

### 用户提供的继续游戏结果

用户转述的 Claude 一百局汇总为：达到 4096 和 8192 各 100 局，16384 为 94 局，32768 为 42 局，65536 为 0 局；最高得分 629420，平均 16336 步，并说明没有形成第二个 32768。这是需要解释的观察，但本次未取得对应源码、种子、逐局日志和终止规则，因此属于**尚未独立核验的汇总**。

如果暂按一百次独立、同分布的完整游戏计算，42/100 的 95% Wilson 区间约为 32.8%–51.8%。它不能与项目的 49/100 直接构成“加深后提升或下降七个百分点”的因果结论：两组版本、配置与随机样本没有对齐。区间重叠也不等于已经证明效果相同。

得分和步数较高，可以说明游戏持续较久，却无法单独定位失败原因。需要区分：算法在 32768 后停止、换用了另一套求解器、继续搜索但残局估值不佳，还是移动或表示边界阻止了目标合并。

## 三 加深搜索与 TD 学习的关系

TD 训练决定 N-tuple 表里的权重；Expectimax 推理则利用已有权重比较未来行动。**提高搜索深度不会自动重新训练模型。** 当前模型评价的是 afterstate，即玩家完成移动、随机新块尚未出现的局面；返回值是未来得分估计，不是“达到 65536 的概率”。[模型与搜索接口](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/API.md)

按当前 JavaScript 实现的口径：

- 1-ply：比较根动作的合并奖励与其 afterstate 估值。
- 2-ply：再完整枚举随机生成的位置和数值，并比较下一次玩家动作。
- 3-ply、4-ply：继续增加相应的生成与决策周期，最后仍依赖同一套叶子估值。

这些定义应以递归终止位置为准，不能只凭其他项目也写了“3-ply”，就认为搜索工作量完全一致。当前构造器只允许常规 `ply` 为 1 或 2；困难局面实际深度直接设为 3。内部递归参数已有通用形式，但固定三层、四层尚未作为公开配置验证。[当前求解器源码](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/ntuple2048.js)

加深可能提前看到堵死、合并次序和空位消耗，减少短视决策；然而叶子估值仍是近似值。如果晚期罕见局面的权重不够可靠，更多搜索也可能沿用甚至放大错误排序。因此，不能承诺单局决策或总体胜率随深度单调改善，更不能把得分提升自动解释成 65536 概率提升。

## 四 外部研究提供了怎样的参照

作者维护的 TDL2048 项目列出以下带 tile-downgrading（DG）的历史成绩。这些是**外部系统的报告值**，不是本项目预测值。[TDL2048 性能表](https://github.com/moporgic/TDL2048#performance)

| 搜索深度 | 达到 32768 的报告比例 | 表中标注的游戏数 |
|---|---:|---:|
| 1-ply | 30.16% | 1,000,000 |
| 2-ply | 48.92% | 100,000 |
| 3-ply | 57.90% | 10,000 |
| 4-ply | 62.00% | 1,000 |
| 5-ply | 67.40% | 100 |
| 6-ply | 72.00% | 100 |

表中趋势支持“更深搜索有可能提高 32768 到达率”，但模型和评估设计不能省略。2021 年论文的最佳配置使用两阶段 8×6 网络、MS-OTD+TC 与 DG，并非当前移植的单套 8×6 基线。论文采用重复训练和评估、报告平均值与置信区间；例如五层为 67.40%±12.21%，六层为 72.00%±12.00%。不能把前者理解为单次一百局中成功 67.4 局，也不应据此自行重建二项置信区间。README 中的两层、四层数据不在论文表 X 中。[2021 年论文，实验设计与表 X](https://arxiv.org/pdf/2111.11090)

**65536 的证据尤其需要分清。** 同一论文将约 0.02% 的达到率归于三层搜索的大规模测试，并明确五层、六层的一百局测试没有出现 65536。因此，不能把 72% 与 0.02% 拼成“六层得到 65536 的成功率”。[2021 年论文，第 8 页](https://arxiv.org/pdf/2111.11090#page=8)

2016 年 MS-TD 研究也显示训练方式的重要性：其普通 TD 配置从一层到三层都未达到 32768，而三阶段 MS-TD 随深度提高得到 0.06%、5.50%、13.78%，各配置测试一万局。这支持把晚期训练覆盖纳入诊断，但这些旧模型的数值同样不能移植为当前模型的胜率。[2016 年论文，第 6 页表 1 与表 2](https://arxiv.org/pdf/1606.07374#page=6)

## 五 冲击 65536 前必须厘清的实现边界

当前实现的关键约束如下：

1. `target` 只允许 4–32768，达到目标后就停止。
2. packed 棋盘每格四位，最大 rank 为 15，即 32768；不存在 rank 16 的合法编码。
3. 每张六格特征表大小为 `16^6`，不能直接索引含 65536 的局面。
4. TD 使用的 `movePacked` 故意不合并两个 rank 15。公开数值移动引擎能合成 65536，不代表 TD 搜索路径也能。

同样，`chooseMove` 接收一个已经包含 65536 的棋盘并返回“目标已达成”，只是在打包前终止，并没有评价或继续规划这个棋盘。[逐接口边界与目标安全](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/API.md)

这里有一个重要的工程区分：

- **只求第一次 65536，合成即结束：** 可以研究在打包前识别两个 32768 的获胜合并，把它作为终止事件，从而不必用现有模型评价 rank 16 棋盘。但必须同步处理移动、奖励、搜索终止和边界测试；只放开目标参数不够。
- **合成 65536 后还要继续：** 需要支持更大 rank 的表示，以及可信的评价办法，例如经过验证的映射或新模型。简单扩展数组长度不会产生训练好的权重。

这些是可行路径分析，尚未实现或验证；目前也没有依据断言必须“大规模重写”，或一定可以通过一个参数完成。

## 六 时间成本与一百局的统计边界

一次额外生成与决策周期，在有 E 个空位时会枚举最多 `2E` 个生成分支，每个分支再检查最多四个方向。实际增长受合法动作、后续空位、目标提前终止以及缓存策略影响，不能用固定倍数外推。

历史独立评估中，第三层仅用于约 12.1% 的动作；两进程总墙钟为 4 分 49 秒，平均每局 5.635 秒，按移动数加权的平均决策耗时 0.398 ms，峰值单进程 RSS 640.70 MiB。这些是指定 Node.js 与云机器上的选择性搜索成绩，不能当作固定三层、四层的速度，也不能把平均值当作尾部延迟。[项目环境与速度记录](https://github.com/Serpens-HBC672/Sudoku/blob/d368eb7870cdd7e8ae400ee67d628ef033c3bbdf/tools/2048-ntuple/EXPERIMENTS.md#环境与速度)

外部还有一个量级参照：Jaśkowski 的研究在其指定网络、单线程 i7-4770K 与置换表条件下，三层约为每秒 1484 步，五层约为每秒 16 步，对应 32768 报告比例为 50% 和 54%，样本分别为 1000 局和 300 局。硬件、模型和样本均不同，不能据此估算本项目耗时；它说明应同时衡量收益与成本，而不是只追求更大的深度数字。[Jaśkowski 论文，第 11 页表 V](https://arxiv.org/pdf/1604.05085#page=11)

对于 65536，**零成功不等于概率为零**。以下仅是独立同分布伯努利模型下的数学说明，并非新游戏实验：

- 一百局零成功时，单侧 95% 精确置信上界约为 2.95%。
- 假设真实概率恰为 0.02%，一百局全部失败的概率约为 98.02%。
- 在同一假设下，要让“至少见到一次成功”的概率达到 95%，需要约 14978 局。

第三个数只涉及看见一次成功，远不足以保证精确估计稀有事件概率。因此，一百局可用于初步比较 32768、运行成本和失败形态，难以单独判定极低概率的 65536 能力。

## 七 后续实验方案与决策标准

以下方案供以后授权执行，本次不据此修改代码或启动测试。

**第一步，先过正确性检查。** 在同一实现中统一支持所需目标和固定深度；核验真实合并规则、四位边界、首个 65536 的终止处理、奖励与特征索引。用小棋盘案例及独立参考递归核对各深度结果，确保求解器始终拿不到种子或未来随机数。未通过这一阶段，深度胜率比较没有解释力。

**第二步，做十局资源试跑。** 使用不进入正式评估的新种子，测量固定两层、三层、四层和选择性三层的耗时、节点数及内存。这一步只用于确定机器与时间预算，不凭十局结果选择“最强深度”后宣称其胜率。随后冻结代码、权重、规则、参数和正式种子清单。

**第三步，做四组配对比较，每组一百局。** 四组使用相同的另一批一百个新种子，共四百局，采用同一套 8×6 权重与随机生成规则；每局持续到无合法移动或首次 65536，途中保留第一次 32768 的记录。相同种子提供配对基础，但动作不同后棋盘轨迹仍会分叉，不能认为各组经历完全相同的局面。

每局至少保存：

- 首次达到 32768、首次同时出现两个 32768、首次达到 65536 的状态及步数。
- 最终棋盘、得分、有效步数、游戏时间、决策延迟中位数与 p95。
- 节点数、实际深度分布、内存、代码及权重哈希。
- 正常结束或超时中止；中止按删失或未完成单独报告，不能偷偷计为输局或删去。

分析时同时报告各组到达率、置信区间，以及同种子下“仅 A 成功／仅 B 成功”的配对结果；比较深度差异可用适合配对二元结果的方法。先明确主要指标与资源上限，避免看完数据再挑最有利的指标。

**最终建议：保留已验证的选择性三层作为对照，优先验证固定三层是否带来与额外耗时相称的增益，再判断固定四层的成本。** 如果目标是 65536，应先确认继续游戏路径正确，再区分搜索视野、晚期估值和稀有事件样本量的影响。现有证据支持开展这样的验证，不支持承诺“再加一层就能过关”。
